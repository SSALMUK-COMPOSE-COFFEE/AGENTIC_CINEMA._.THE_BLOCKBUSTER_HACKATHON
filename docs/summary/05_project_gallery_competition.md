## 1. 갤러리 현황

### 1.1 결론: **갤러리는 아직 비공개(미공개) 상태다**

`https://agentic-cinema.devpost.com/project-gallery` 및 `?page=2`를 모두 조회한 결과, 두 페이지 모두 동일한 메시지만 노출된다.

> "The hackathon managers haven't published this gallery yet, but hang tight!"

즉 **현재 시점에서 확인 가능한 제출 프로젝트는 0건이며, 프로젝트별 이름·태그라인·트랙·Built With 태그를 수집하는 것은 물리적으로 불가능**하다. 이는 갤러리가 비어 있어서가 아니라, Devpost 운영진이 **마감 이후 심사 단계에서 일괄 공개하는 정책**을 적용했기 때문이다. Google Cloud가 주최하는 대형 상금 해커톤(ADK Hackathon, All Things Agentic 등)에서 흔한 운영 방식으로, 제출 마감 직후~심사 개시 사이에 갤러리가 열리는 것이 일반적이다.

따라서 본 문서의 2절(주목할 프로젝트 요약)은 **실측 데이터가 아니라, 동일 주최자·동일 성격의 직전 해커톤 갤러리(공개된 것)에서 추출한 패턴**으로 대체한다. 이 점을 명시적으로 밝혀 둔다.

### 1.3 트랙 분포 추정

실제 제출 분포는 확인 불가하나, 다음 근거로 **편중이 심할 것**으로 추정한다.

* **Replit / ClickHouse 트랙 과밀 예상** — 진입 장벽이 가장 낮다. Replit은 별도 크레딧 코드 신청 폼까지 제공되고, ClickHouse는 "쿼리 몇 개 붙이면 통합 인정"으로 보이기 쉽다. 초보~중급 참가자가 몰린다.
* **IBM(watsonx) 트랙 중간** — watsonx Code Assistant는 "영화 제작 도구"라는 주제와 접점을 찾기 까다로워, 억지 결합이 많아질 가능성이 높다.
* **Grafana / Parallel 트랙 상대적 희소** — Grafana는 관측성 도구라 미디어 워크플로와 붙이려면 설계가 필요하고, Parallel은 인지도가 낮다. **경쟁률 대비 기대값이 가장 높은 트랙**이다.

> 상금이 트랙별로 **동일하게** 걸려 있다는 점이 핵심이다. 9,904명이 5개 트랙에 균등 분포하지 않으므로, **트랙 선택 자체가 전략 변수**다.

### 1.4 참고: 규정에서 확인된 결정적 제약

* Google Cloud AI 도구(Gemini 계열, BigQuery ML)와 **선택한 트랙의 파트너 제품만** 사용 가능.
* **"No other AI models, agent frameworks, or AI APIs are permitted"** — OpenAI/Anthropic/LangChain 등 타사 모델·에이전트 프레임워크 사용 금지. (LangGraph, CrewAI 등도 위험. ADK / Agent Builder / Agent Engine 사용이 안전)
* 대회 기간 중 **신규 제작물**이어야 함. 기존 프로젝트 재활용 불가.
* 웹 / Android / iOS 중 하나에서 동작.
* 공개 저장소 + OSS 라이선스 + 3분 이내 데모 영상(YouTube/Vimeo, 영어 또는 영어 자막) + 호스팅된 프로젝트 URL.
* **주최 측 공식 강조점**: "AI로 만든 영화 콘테스트가 아니다. 각본가·제작 스태프가 **실제로 쓸 수 있는 도구**를 만들어라."

## 2. 주목할 프로젝트 요약 (대체 자료: 동일 주최 직전 해커톤 상위작)

> **주의**: 아래는 Agentic Cinema 제출작이 아니다. Google Cloud ADK Hackathon(공개 갤러리, 총 476건 제출)의 상위 노출작이며, **"Google Cloud 심사위원이 무엇을 뽑는가"를 역산하기 위한 프록시 데이터**다.

### 2-1. SalesShortcut — 멀티에이전트 SDR 시스템
* **문제**: 영업 개발 담당자(SDR)의 리드 발굴·검증·아웃리치 반복 노동.
* **에이전트 동작**: 리드 수집 → 자격 검증 → 개인화 메시지 작성 → 후속 관리를 에이전트별로 분업.
* **스택**: ADK 멀티에이전트, Agent Engine, Cloud Run.
* **시사점**: **"역할 분리된 멀티에이전트 + 실무 직군 대체"** 조합이 최상위 수상 공식. 단일 에이전트보다 오케스트레이션이 유리하게 채점된다.

### 2-2. Bleach — ADK용 비주얼 에이전트 빌더
* **문제**: 에이전트를 코드로만 조립해야 하는 진입 장벽.
* **에이전트 동작**: 자연어로 에이전트를 설명하면 시각적 그래프로 설계·즉시 테스트.
* **시사점**: **메타 도구(도구를 만드는 도구)**가 강하게 먹힌다. Agentic Cinema로 치환하면 "감독이 자기 파이프라인을 직접 조립하는 에디터"에 해당.

### 2-3. Particle Physics Agent — 자연어 → 검증된 파인만 다이어그램
* **시사점**: **검증 가능한 출력(physical laws 검증)**을 내는 에이전트가 "환각 데모"와 차별화되어 높게 평가됨. 미디어 도메인에서는 "연속성 검증", "예산 제약 검증", "촬영 일정 실행가능성 검증"이 같은 역할.

### 2-4. TradeSage AI — 멀티에이전트 금융 분석
* **스택**: ADK + Agent Engine + Cloud Run + Vertex AI 풀스택.
* **시사점**: 심사 항목 "Technological Implementation"은 **Google Cloud 제품을 몇 개 실제로 엮었는가**로 사실상 채점된다. 단일 Gemini API 호출만 있는 제출은 상위권에서 사라진다.

### 2-5. Voltaros — GKE 카오스 엔지니어링 자동화
* **시사점**: **관측성/운영 도메인 에이전트**가 실제로 수상권에 든 사례. 이번 대회 **Grafana 트랙의 직접적 선례**로 볼 수 있다.

### 2-6. Edu.AI / Nexora-AI / InnerVerse / Owlspeak / Vyralflow
* 교육·저널링·커뮤니케이션·SNS 캠페인 자동화. **가장 붐비는 카테고리**이자, 상위권에서는 "지역 특수성(브라질 교육 제도)"처럼 **구체적 타깃을 못 박은 것만 살아남았다.**

### 2-7. 종합 추론: Agentic Cinema에서 실제로 몰릴 것으로 보이는 아이템

주최 측 리소스 페이지가 제시한 "영감 목록"이 곧 **레드오션 목록**이다. 다수 참가자가 이 목록을 그대로 구현할 것이다.

1. 각본 분석 / 스크립트 브레이크다운 (**최다 예상**)
2. 영상 전사 + 타임스탬프 인덱싱
3. VFX 무드보드 / 컨셉아트 생성 (Imagen)
4. 사운드트랙·효과음 생성 (Lyria)
5. 멀티스피커 대사·팟캐스트 생성 (Gemini TTS)
6. 배우 보이스오버 감정 분석
7. 제작 스케줄 자동화
8. 박스오피스 리포팅 질의 (**ClickHouse 트랙 최다 예상**)
9. 인터랙티브 대본 리허설 도구
10. 비주얼 에셋 라이브러리 큐레이션

## 3. 트렌드 · 패턴 분석

### 3.1 확실히 붐빌 패턴 (차별화 실패 위험 구간)

| 패턴 | 설명 | 위험 |
| --- | --- | --- |
| **"스크립트 넣으면 요약/분해해 줍니다"** | PDF 각본 업로드 → Gemini 롱컨텍스트로 씬·캐릭터·소품 추출 | 구현 난도가 낮아 수백 건 중복. Gemini 자체 능력이 90%를 하고 개발자 기여가 안 보임 |
| **"무드보드 생성기"** | 프롬프트 → Imagen 이미지 그리드 | 에이전트가 아니라 래퍼(wrapper)로 보임. "Technological Implementation" 최저점 |
| **"박스오피스 대시보드에 챗봇"** | ClickHouse에 흥행 데이터 넣고 text-to-SQL | ClickHouse 트랙에서 가장 뻔한 답. 데이터셋도 다들 같은 공개 데이터 사용 |
| **"AI 영화 만들기"** | Veo/Imagen으로 단편 생성 | **규정 위반에 가까움.** 주최 측이 "AI 생성 영화 대회가 아니다"라고 명시 |
| **단일 에이전트 챗 UI** | 채팅창 하나 + 툴 몇 개 | 심사 "Design(완결된 제품 경험)"에서 감점 |

### 3.2 상위권 공통 패턴 (모방할 가치가 있는 것)

1. **역할 분업형 멀티에이전트 오케스트레이션** — Planner / Researcher / Critic / Executor 구조. Google Cloud가 ADK를 밀고 있으므로 채점에 직접 반영된다.
2. **Google Cloud 제품 스택 다층 사용** — Gemini(추론) + Vertex AI Search 또는 BigQuery(그라운딩) + Cloud Run(배포) + Secret Manager. 4개 이상 엮으면 기술 점수가 확실히 올라간다.
3. **검증 루프(Verifier)** — 생성 결과를 제약조건에 대해 다시 검사하는 단계가 있으면 "환각 데모"와 분리된다.
4. **구체적 실무 사용자 명시** — "영화인"이 아니라 "6주차 프리프로덕션 단계의 1st AD", "독립영화 라인 프로듀서" 수준으로 좁힌 것.
5. **비동기·백그라운드 실행** — "에이전트가 알아서 오래 돌아간다"는 서사. Parallel Task MCP가 정확히 이 패턴을 지원한다.
6. **파트너 제품이 장식이 아니라 필수 부품** — 파트너 제품을 빼면 프로젝트가 작동하지 않아야 한다.

### 3.3 실패 패턴

* 파트너 제품을 **마지막 날 억지로 끼워 넣기** (예: 로그를 Grafana에 던져 놓고 "Grafana 통합"이라 주장) → 트랙 심사에서 즉사.
* **호스팅 URL 부재 / 저장소 미공개 / 3분 초과 영상** → 형식 실격. 매 해커톤마다 상당수가 여기서 탈락한다.
* 타사 모델·프레임워크 잔재(LangChain import, OpenAI SDK) → 규정 위반.
* 데모 영상이 "슬라이드 발표" → Design·Impact 동시 감점. **실제 화면에서 에이전트가 일하는 장면**이 필요하다.

## 4. 트랙별 빈틈 · 차별화 기회

### 4.1 IBM 트랙 (watsonx Code Assistant)
* **붐빌 것**: 별로 없음. 오히려 "영화와 코드 어시스턴트가 무슨 상관인가"에서 다들 막힌다.
* **빈틈**:
  * **VFX/파이프라인 TD 도구** — Houdini/Nuke/Blender **Python 스크립트를 에이전트가 생성·리팩터링**하는 도구. 실제 VFX 스튜디오의 최대 반복 노동이며, watsonx Code Assistant의 코드 현대화 기능과 정확히 맞물린다.
  * **레거시 방송 파이프라인 현대화** — 방송국의 낡은 배치 스크립트/Perl 자동화를 watsonx로 현대화 + Gemini가 도메인 맥락 부여.
  * **게임 시네마틱/엔진 스크립트 자동화** — 컷신 시퀀스 코드 생성.
* **차별화 포인트**: "생성된 코드를 샌드박스에서 실제 실행해 검증"까지 넣으면 이 트랙 1위권.

### 4.2 Grafana Labs 트랙
* **붐빌 것**: 렌더팜/GPU 사용률 대시보드.
* **빈틈**:
  * **프로덕션 자체를 관측 대상으로 삼기** — 촬영 일정·예산 소진·씬 완료율·배우 콜타임을 시계열 메트릭으로 모델링하고, **에이전트가 이상 징후(일정 지연 확산)를 감지해 스케줄 재편성을 제안**. "관측성 = 서버"라는 고정관념을 깬 것 자체가 Quality of Idea 점수다.
  * **Grafana Incident/Alerting을 에이전트 트리거로 사용** — 알람 → Gemini 에이전트가 원인 분석 → 대응안. 단방향 대시보드가 아니라 **양방향 루프**.
  * **라이브 방송/스트리밍 QoE 에이전트** — 버퍼링·비트레이트 이상 감지 후 자동 진단.
* **차별화 포인트**: Grafana를 **출력(대시보드)이 아니라 입력(에이전트의 감각기관)**으로 쓰는 설계. 여기서 갈린다.

### 4.3 Parallel 트랙 ★ 최고 기대값
* **붐빌 것**: 인지도가 낮아 제출 자체가 적을 가능성. **경쟁률 대비 상금이 가장 유리한 트랙.**
* **Parallel 제품 특성**: Task API / Task MCP — **비동기 딥리서치 + 데이터셋 enrichment**. 여러 리서치 태스크를 병렬로 던지고 논블로킹으로 회수.
* **빈틈**:
  * **시대고증·리서치 에이전트** — 시대극 각본에서 "1974년 서울의 택시 요금", "해당 시기 실제 존재한 브랜드" 등을 **씬 단위로 자동 추출해 병렬 리서치 → 고증 오류 리포트**. 각본가·미술감독의 실제 업무이며, 웹 딥리서치가 필수라 Parallel이 대체 불가능한 부품이 된다.
  * **클리어런스/권리 조사** — 대본 속 상표·음악·실존 인물 언급을 뽑아 **법무 클리어런스 리스크 리포트** 생성. 실제 제작사가 돈 주고 사는 업무.
  * **로케이션 헌팅 에이전트** — 씬 설명 → 조건 만족 실제 장소를 병렬 리서치 + 허가 절차·비용·계절 제약 enrichment.
  * **캐스팅/비교작품 시장조사** — 유사 장르 흥행 이력, 배우 가용성·최근 작품 병렬 조사.
* **차별화 포인트**: "한 편의 각본 → 수십 개 병렬 리서치 태스크 팬아웃 → 통합 제작 리스크 보고서". **팬아웃 규모를 데모에서 시각적으로 보여주는 것**이 결정타.

### 4.4 ClickHouse 트랙
* **붐빌 것**: 박스오피스 text-to-SQL 챗봇 (**확실히 최다 중복**).
* **빈틈**:
  * **프레임/샷 단위 벡터 + 메타데이터 검색** — ClickHouse를 벡터 스토어로 써서 **"비 오는 밤, 인물 2명, 클로즈업" 같은 질의로 수만 개 샷을 실시간 검색**. Gemini 멀티모달로 샷 임베딩·캡션 생성 → ClickHouse에 적재. 편집 어시스턴트로서 실사용 가치가 명확하고, ClickHouse의 진짜 강점(대용량 스캔 속도)을 쓴다.
  * **더빙/자막 QC 로그 분석** — 대사 타임코드·립싱크 오차를 대규모로 적재해 이상치 탐지.
  * **관객 반응 실시간 분석** — 시사회/스트리밍 이탈 지점 초 단위 적재 → 에이전트가 "몇 분 몇 초에서 이탈 급증, 해당 씬은 X" 형태로 편집 제안.
* **차별화 포인트**: **"SQL을 대신 써 주는 챗봇"에서 벗어나 ClickHouse를 에이전트의 장기 기억/검색 인덱스로 쓸 것.**

### 4.5 Replit 트랙
* **붐빌 것**: Replit에 배포한 평범한 웹앱 + "Replit로 만들었습니다" 수준의 통합. 물량 최다 예상, 평균 품질 최저 예상.
* **빈틈**:
  * **에이전트가 Replit에 코드를 생성·배포까지 하는 구조** — 예: 감독이 원하는 인터랙티브 스토리보드/프리비즈 도구를 Gemini가 **코드로 생성해 Replit에 실배포**, 링크를 스태프에게 공유. 즉 Replit을 **에이전트의 실행 런타임/출력 매체**로 사용.
  * **각본 → 플레이 가능한 인터랙티브 프리비즈 앱 자동 생성** — 매 씬을 실행 가능한 프로토타입으로.
* **차별화 포인트**: Replit이 "내가 배포한 곳"이 아니라 **"에이전트가 쓰는 도구"**여야 한다. 이 구분 하나로 상위 5% 안에 든다.

## 5. 우승 전략 제언

### 5.1 트랙 선택
1순위 **Parallel** (희소 + 제품 특성이 미디어 리서치와 자연스럽게 맞물림)
2순위 **Grafana** (희소 + 발상 전환만으로 Quality of Idea 점수 확보)
3순위 **IBM** (희소하지만 주제 결합 난도 높음 — VFX 스크립팅으로 풀면 유효)
회피 **ClickHouse / Replit** (뻔한 답이 넘칠 것 — 진입하려면 4.4/4.5의 빈틈 각도로만)

### 5.2 심사 기준별 대응 체크리스트

**① Technological Implementation (Google Cloud + 파트너 활용도)**
- [ ] ADK 또는 Agent Builder 기반 **멀티에이전트** 구조 (단일 프롬프트 체인 금지)
- [ ] Google Cloud 제품 4개 이상 실사용: Gemini(멀티모달·롱컨텍스트) + Vertex AI Search 또는 BigQuery(그라운딩) + Cloud Run(호스팅) + Secret Manager
- [ ] 파트너 제품을 **MCP로 연결** (주최 측이 MCP를 명시적으로 밀고 있음 — 가산점 구간)
- [ ] 파트너 제품 제거 시 프로젝트가 **작동 불능**임을 README/영상에서 증명
- [ ] 타사 모델·프레임워크 **완전 제거** (import 잔재까지 확인)

**② Design (완결된 제품 경험)**
- [ ] 채팅창 하나가 아니라 **실무 워크플로 화면** (타임라인, 씬 리스트, 리포트 뷰)
- [ ] 에이전트의 **진행 상태·중간 사고 과정 가시화** (어떤 태스크가 병렬로 돌고 있는지)
- [ ] 사람이 개입해 수정·승인하는 **Human-in-the-loop 지점** 명시
- [ ] 호스팅 URL이 **실제로 열리고 게스트도 써 볼 수 있어야 함** (로그인 벽 금지)

**③ Potential Impact (실제 문제 해결)**
- [ ] 타깃을 직군 단위로 못 박기 (예: "독립영화 라인 프로듀서", "VFX 파이프라인 TD")
- [ ] **시간/비용 절감을 숫자로** 제시 ("수작업 6시간 → 4분")
- [ ] 가능하면 실제 공개 각본(퍼블릭 도메인 시나리오)으로 데모 — 합성 데이터보다 설득력 압도적
- [ ] 현업 종사자 한 줄 코멘트라도 확보하면 강력

**④ Quality of Idea (창의성)**
- [ ] 주최 측 "영감 목록" 10개를 **그대로 하지 않기** (그게 곧 레드오션 목록)
- [ ] 파트너 제품의 **비관습적 용도** 찾기 (Grafana=제작 관측, ClickHouse=샷 검색 인덱스, Replit=에이전트 런타임)
- [ ] 한 문장 포지셔닝: "X를 위한 Y" 형태로 즉시 이해되게

### 5.3 제출물 실행 전술

* **영상 3분은 절대 초과 금지.** 구성: 0:00–0:20 문제 제시(현업 고통) → 0:20–2:20 **실제 화면에서 에이전트 동작 라이브** → 2:20–3:00 아키텍처 다이어그램 + Google Cloud/파트너 제품 명시. 슬라이드 낭독 금지.
* **README에 아키텍처 다이어그램 필수.** 심사위원은 코드를 다 읽지 않는다. 다이어그램에 Google Cloud 제품명과 파트너 제품명을 **박스로 명시**하면 기술 점수가 직접 올라간다.
* **OSS 라이선스 파일(MIT/Apache-2.0) 반드시 커밋.** 누락 시 형식 실격.
* **마감(KST 09-10 06:00) 최소 12시간 전 제출.** Devpost 마감 직전 트래픽 폭주로 업로드 실패 사례가 매번 발생한다.
* **갤러리 공개 후 재점검**: 마감 직후 갤러리가 열리면 실제 경쟁작을 확인해, 심사 기간 중 허용되는 범위(README·영상 설명란 등)에서 포지셔닝 문구를 다듬을 수 있다.

### 5.4 한 줄 결론

> **9,904명이 등록했지만 실제 완주 제출은 그 5~10%인 500~1,000건 수준일 가능성이 높고, 그중 5개 트랙으로 쪼개지면 트랙당 100~200건이다. 상위 3위 안에 들려면 "각본 요약기"가 아니라, 파트너 제품이 없으면 성립하지 않는 구조 + 실무 직군 하나를 정확히 겨냥한 완결된 도구여야 한다. Parallel 트랙의 "시대고증·클리어런스 리서치 에이전트"가 현재 확인된 정보 기준 가장 유리한 조합이다.**
